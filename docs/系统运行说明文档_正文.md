## 二、系统架构

系统为四层结构，层间只通过固定接口通信：

```
   平台 (contest_harness SDK)
        │  宿主提供：rnd.parent / rnd.data / rnd.model / rnd.transport
        ▼
┌───────────────────────────────────────────┐
│ Controller  layers/controller/round.py    │  协议的唯一所有者
│  轮序：open_parent → read_public → plan  │
│  → measure_parent → build_candidate →     │
│  measure_candidate → decide → record →    │
│  consult_the_model → submit → finish      │
└───────────────────────────────────────────┘
        │                    │
        ▼                    ▼
┌──────────────────┐  ┌──────────────────┐
│ Model 层          │  │ Profile 适配层   │
│ layers/model/     │  │ adapters/        │
│ checkpoint 账本   │  │ profile_a/b/c    │
│ metrics 状态机    │  │ 假设库·度量口径  │
└──────────────────┘  │ ·选型视图·护栏   │
        │             └──────────────────┘
        ▼
┌───────────────────────────────────────────┐
│ Reference  contest_baselines/model.py     │
│ 平台工件格式 + 参考前向传播                │
└───────────────────────────────────────────┘
```

**镜像内不含研究代码**（`harness/`、`research/`、`tracks/` 都不在镜像里）。
原因见第六节「镜像构建说明」。

## 四、镜像运行流程

### 4.1 平台如何调用

平台通过固定路径进入参赛者代码，**只有一个入口**：

```bash
python3 /app/harness.py describe   # 声明支持的任务：classification / regression
python3 /app/harness.py train       # 执行一轮闭环
python3 /app/harness.py predict     # 逐样本作答
```

`describe` 会被平台在预检时调用，用来核对任务声明。`train` 被平台按轮次
反复调用。`predict` 在评测阶段按样本逐行调用。

### 4.2 一轮 `train` 的内部流程

```
① open_parent      读父工件（rnd.parent.path，校验平台声明摘要）
                   → 检查 task 与 meta['task'] 一致、meta['paths'] 存在
② read_public      读训练集/验证集投影，校验两侧样本 ID 不重叠
③ plan             从适配器的假设库里选本轮假设（由轮次 + 历史驱动）
④ measure_parent   在公开验证集上测父模型
⑤ build_candidate  从父模型精确副本出发，应用假设的训练改动并训练
⑥ measure_candidate 在同一个验证集上测候选
⑦ decide           compare_joint() 判决 + 全量护栏 + 方向一致性
⑧ record           写账本 + 写 SwanLab 记录
⑨ consult_the_model 向平台模型复核本次读数（真实模型调用）
⑩ submit           采纳则交候选工件，否则保留父模型
⑪ finish           声明本轮结果
```

### 4.3 `predict` 的内部流程

```
读 CONTEST_ARTIFACT_PATH → 加载参考格式工件 → 调用参考前向传播 → 返回一个样本
```

前向传播**用的是平台随包提供的参考实现**，所以平台的测量口径与我们看到的
完全一致，不存在「自己测分、平台测分两套标准」的偏差。

## 五、关键参数与调节点

### 5.1 运行时环境变量

| 变量 | 用途 | 平台是否注入 |
|---|---|---|
| `CONTEST_APP_ROOT` | 镜像内代码根目录（默认 `/app`） | 是 |
| `CONTEST_ARTIFACT_PATH` | 当前工件的 checkpoint 路径 | 是（predict 阶段）|
| `CONTEST_PARENT_ROOT` | 父工件根目录（本地调试用）| 否（平台注入 `rnd.parent.root`）|

**镜像内不含任何 API Key、端点或 HTTP 客户端**——模型访问只经
`rnd.model` / `rnd.transport`（平台宿主实现）。

### 5.2 策略层参数

| 参数 | 位置 | 当前值 | 含义 |
|---|---|---|---|
| `MODEL_CALL_ATTEMPTS` | `layers/controller/round.py` | 3 | 单轮模型调用的尝试次数 |
| `MODEL_CALL_BACKOFF` | 同上 | 3.0 s | 尝试间的退避基数 |
| `MODEL_TOKEN_BUDGET` | 同上 | 1024 | 复核请求的 token 上限 |
| epoch 基础预算 | `strategies.py` | 65（C 方向 ×0.5）| 随轮次线性递增至上限 |
| 全量护栏容忍度 | `adapters/base.py` | 0.05 | 主指标最多允许劣化 5% |
| 相对退化度 α | `adapters/profile_c.py` | 0.5 | 相对退化度加权强度 |

### 5.3 假设库与适配器

| 适配器 | 方向 | 假设库首项 | 选型视图 |
|---|---|---|---|
| `profile_a.py` | A | `the-batch-is-mixing-scales` | 无（全量即协议）|
| `profile_b.py` | B | 见文件 | 无 |
| `profile_c.py` | C | **`the-degradation-is-relative`** | `late_rmse`（**只记录，不裁决**）|

C 方向的 `weight_horizon()` 返回 `None`，即**关闭绝对阈值加权**；这是第三节
所述根因修复的落点。

## 六、镜像构建说明

### 6.1 构建与导出

```bash
# 构建
docker build -t zhixun-engine-b .

# 导出为平台要求的 tar（< 50M）
docker save zhixun-engine-b -o zhixun-engine-linux-amd64.tar
```

### 6.2 为什么镜像里只有提交代码

镜像**只携带提交物，不携带实验室**。`harness/`、`research/`、`tracks/`
都不在镜像里，原因有两条，都是实测踩到的：

1. **一个名为 `harness` 的包会遮蔽 `harness.py`**。CPython 先解析包再解析
   同名模块，于是 `import harness` 落进包里，SDK 入口对任何基于名称的
   检视都变得不可见。
2. **`harness/llm.py` 是唯一讲 OpenAI 形状 HTTP 协议的文件**，
   `harness/experiments.py` 是一个二阶段轴承 RUL 模型。检视方在找
   「会调模型的闭环」时会命中研究代码，进而判定该提交只服务回归任务。

研究运行时保留在**源码仓库**、**源码链接**和 `Dockerfile.research` 中。

### 6.3 镜像内容清单

```
/app
├── harness.py                 # 唯一入口（describe / train / predict）
├── contest_submission.py      # train(rnd) / predict(sample, model_dir)
├── contest_baselines/         # 参赛实现（layers / adapters / model 等）
├── contest_harness_sdk/       # 平台 SDK
├── requirements.txt
├── MANIFEST.json              # 镜像内文件清单与摘要
├── README.md
└── LICENSE
```

## 八、故障诊断

| 现象 | 原因 | 处理 |
|---|---|---|
| `运行失败 / 上游 HTTP 504` | 平台模型网关超时或上游模型服务波动 | **平台侧问题**，非本提交代码问题。平台不会自动重发，需**手动重新发起试运行**；正式评测额度不会因试运行失败而消耗 |
| `PREFLIGHT_INCOMPATIBLE` | 镜像里的训练/预测入口签名、输入输出格式或运行环境不符合赛事接口规范 | 核对 `harness.py` 的 `describe/train/predict` 三个入口与 `TASKS` 声明 |
| `the parent checkpoint declares no feature schema` | 父工件 `meta['paths']` 缺失 | 平台侧工件问题 |
| `the training and validation sample IDs overlap` | 数据投影异常 | 平台侧数据问题 |
| 模型调用超时 | 上游 27B 单次响应实测可达 **141~825 秒** | 属平台网关超时设置问题，需联系管理员核查；`_call_model` 已内置 3 次重试与退避 |

## 九、安全声明

1. **无恶意代码**：镜像只有一个入口，全部源码公开可审。
2. **无未授权网络访问**：镜像内无 HTTP 客户端、无 API Key、无外部端点。
3. **父模型只读**：通过 `rnd.parent.path` 打开并校验摘要，绝不写回。
4. **受控迭代**：度量护栏 + 方向一致性 + 受控 epoch 预算 + 假设驱动的更新。
5. **不触碰隐藏测试**：只读 `rnd.data.train_path` / `rnd.data.validation_path`，
   代码中不存在任何读取隐藏标签的路径。
6. **仅用允许的数据与模型**：驱动 Harness 的大模型为 PyTRiO 训练所得的
   `planner-27b-sft-v1`，已在表单如实申报。
