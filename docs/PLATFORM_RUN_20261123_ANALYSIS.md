## 3. 为什么上线了却一点没变

### 3.1 上一次跑的**不是**那个坏候选

我此前的判断是「12% 守门放行了全量 +9.95% 的候选，导致隐藏分 56.253」。
**这个判断是错的**，平台记录否定了它：

| | 12% 版本（本地演练） | 11/22 平台实跑 | 11/23 平台实跑 |
|---|---:|---:|---:|
| C 第 3 轮候选 full rmse | **57.4199** | 52.0024 | 52.0024 |
| C 第 3 轮 rel | +9.95% | **−0.43%** | −0.43% |
| C 第 3 轮是否采纳 | **是** | 否 | 否 |

平台那次的第 3 轮候选全量反而**变好了** 0.43%，在 12% 和 5% 下都会被否决。
**平台根本没有跑那个 +9.95% 的坏候选。**

结论：**12% 守门不是 56.253 的成因**，此前归因错了。

### 3.2 真正的原因是公开集与隐藏集之间约 +10% 的系统性偏移

平台 C 方向最终采用第 5 轮候选：

```
公开验证 rmse : 51.111160
隐藏测试 rmse : 56.25329        <- 恶化 10.06%
静态基线      : 52.8686
```

也就是说，**在公开集上被选中的「最优」候选，搬到隐藏集上比基线还差 6.40%**。
这个偏移（+10.06%）是选型口径与隐藏协议不匹配造成的，
把守门从 12% 收到 5% 动不了它 —— 因为被守门放行的候选**本身**在隐藏集上就是退化的。

**问题**：公开集上 `late_rmse` 与 `full rmse` **频繁反向**。
并列判据要求两者同时改善，于是：

- 第 2 轮：全量好了 **1.05**（52.2253 → 51.1796），切片只差 0.32 → **被否决**

最终停在第 5 轮（51.1112），而不是公开集最好的第 7 轮（50.8784）。
按公开集口径，我们**主动放弃了更好的模型**。

平台记录里给的拒绝理由是：

> the two readings disagree (late_rmse 38.5199 -> 38.8439,
> full rmse 52.2253 -> 51.1796), so the candidate is not adopted

## 5. 待决的两件事

1. **并列判据是否要放松。** 当前规则在切片与全量反向时一律否决，
   会系统性地错过「全量明显变好」的候选。可选：切片变差幅度小于某个容差
   （如 1%）时放行，或改成加权合成单一评分。
2. **公开集 → 隐藏集 +10.06% 偏移是主因。** 这是不达标（56.253 > 52.8686）
   的真正原因，与守门容差无关。需要另找口径（留一轴承 / 全新工况协议，
   或直接以官方 `checkpoint.npz` 为准绳做校准）。
